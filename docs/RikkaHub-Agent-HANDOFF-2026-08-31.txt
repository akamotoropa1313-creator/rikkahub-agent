2. Implemented behavior

- Codex App Server 0.146 thread/start now receives the conversation-owned RikkaHub Assistant's
  client-hosted dynamic tool specifications.
- item/tool/call server requests retain string/numeric JSON-RPC IDs, validate thread/turn/tool/
  namespace/argument context, apply the hardline safety floor, use existing approval scopes, obey
  the per-turn runtime budget, execute through the Android RikkaHub Tool implementation, and return
  inputText/inputImage/inputAudio content items to App Server.
- The selected Assistant's local tools are exposed. This includes termux_run_command when Termux is
  enabled for that Assistant. The Codex process does not need openclaw, clawhub, node, npm, npx, or
  a Termux binary inside /workspace; the RikkaHub/Android bridge performs the invocation.
- Every Assistant-enabled Skill remains enabled together. Codex owns use_skill; RikkaHub also
  exposes its non-conflicting read-only Skill accessor where selected.
- Only MCP servers/tools selected by the conversation-owned Assistant are exposed. Unicode,
  punctuation, and overlong MCP labels are converted to stable unique ASCII names within Codex's
  64-character function-name limit instead of rejecting the server.
- ask_user remains interactive. The Codex-generated question card sends the user's answer directly
  to the pending item/tool/call response and never executes ask_user's headless fallback in the
  visible chat path.
- Runtime profile refresh compares the Assistant Skill profile, tool schema fingerprint, Assistant/
  headless execution identity, and generated developer instructions. Changing the Assistant,
  prompts, Skills, tools, MCP surface, or headless context therefore cannot keep stale closures.
- Room database version is 32. codex_app_server_session_bindings stores dynamic_tools_fingerprint.
  App Server 0.146 cannot override dynamicTools on thread/resume, so a changed fingerprint replaces
  the durable thread before the next turn instead of silently retaining a stale tool surface.
- Codex App Server account synchronization uses the existing RikkaHub Codex provider's login/token
  through the external-token bridge. The control center does not own a second independent browser
  login.
